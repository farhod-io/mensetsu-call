💻 Yapon IT Muhandislik & Texnik Savollar (Tech Check) N+1, REST vs GraphQL, React, Xavfsizlik va Git arxitekturasi
Database & Performance
Q1: 「N+1問題」とは何ですか？実務ではどうやって対策しますか？
N+1 muammosi nima va u amaliyotda qanday hal qilinadi?
【回答例】
「N+1問題とは、親レコードを1回取得した後、関連する子レコードを取得するためにループ内でN回の追加SQLクエリが発行され、データベースに過度な負荷がかかる現象です。
【対策】：ORM（PrismaやTypeORMなど）においてEager Loading（preload、include）やJOINを活用し、クエリを分割せず1〜2回のクエリで一括取得することで解決いたします。」
💡 O'zbekcha: Bitta asosiy ro'yxatni olgach, har bir qatordagi bog'langan ma'lumot uchun bazaga N marta qayta so'rov yuborilib tizim sekinlashishi. Yechimi: Eager Loading (birlashtirilgan bitta SQL so'rov) orqali birdaniga tortib olish.
API Design
Q2: REST APIとGraphQLの違いと、それぞれのメリット・デメリットは？
REST API va GraphQL farqlari, ularning afzallik va kamchiliklari nimalardan iborat?
【回答例】
「RESTはリソースごとにURLが固定されており、HTTPメソッドとキャッシュ設計がシンプルで導入しやすい反面、不要なデータ取得（Over-fetching）や複数回リクエスト（Under-fetching）が発生しやすいです。
一方GraphQLは単一エンドポイントでクライアントが必要なフィールドのみを指定して取得できるため、通信量を最小化できますが、キャッシュ設計やクエリの複雑化対策が必要です。」
💡 O'zbekcha: REST sodda va standart, lekin ortiqcha yoki yetishmovchi ma'lumot muammosi bor. GraphQL bitta so'rovda faqat kerakli maydonlarni tortadi, mobil tarmoqlarda juda yengil, lekin kesh qilish nisbatan murakkabroq.
Frontend & React
Q3: ReactのuseMemoとuseCallbackの使い分けについて教えてください。
React'da useMemo va useCallback xuklari qanday mezon bilan farqlanadi va ishlatiladi?
【回答例】
「useMemoは『計算結果の値』をキャッシュ（メモ化）し、依存配列が変わらない限り重い計算処理の再実行を防ぎます。
一方useCallbackは『関数そのものの参照』をメモ化し、親コンポーネントが再レンダリングされても新しい関数インスタンスが生成されるのを防ぐことで、子コンポーネントの不要な再描画を抑止します。」
💡 O'zbekcha: useMemo — og'ir hisob-kitoblar natijasini keshlaydi. useCallback — funksiya havolasini saqlab, child komponentlarning qayta render bo'lishini to'xtatadi.
Web Security
Q4: SQLインジェクション、XSS、CSRFの対策は具体的にどう行いますか？
SQL Injection, XSS va CSRF xurujlariga qarshi qanday xavfsizlik choralari ko'riladi?
【回答例】
「1. SQLインジェクション：文字列連結を避け、プレースホルダ（Prepared Statements）を用います。
2. XSS：入力値のエスケープ処理とReactのJSX自動エスケープ、およびCSPヘッダーを設定します。
3. CSRF：ワンタイムのCSRFトークン検証と、CookieのSameSite属性をStrictまたはLaxに設定します。」
💡 O'zbekcha: SQLi — Prepared Statements (parametrlashtirilgan so'rovlar). XSS — HTML belgilarni tozalash (escaping) va CSP. CSRF — SameSite cookie va himoya tokenlari.
Git & Team Workflow
Q5: GitのRebaseとMergeの違い、チーム開発でのベストプラクティスは？
Git rebase va merge farqi nima va jamoada qaysi biri qachon ishlatiladi?
【回答例】
「Mergeは分岐と統合の履歴をすべて残すため安全ですが、コミットグラフが複雑になります。
Rebaseはコミット履歴を1本の直線（リニア）に整えるため履歴が綺麗になりますが、公開ブランチでのForce Pushは危険です。
実務では、自分の作業ブランチをmainに追従させる時はRebaseを行い、PRをmainへマージする際はSquash & MergeまたはMerge Commitを活用します。」
💡 O'zbekcha: O'z tarmog'ingizda ishlayotganda rebase bilan toza ushlash, asosiy tarmoqqa (main) qo'shayotganda esa PR orqali merge qilish eng to'g'ri yapon standartidir.
Architecture
Q6: モノリスとマイクロサービスのトレードオフはどう考えますか？
Monolit va Mikroxizmatlar arxitekturasi o'rtasidagi tanlov va balansga qanday qaraysiz?

「開発初期や小規模フェーズでは、デプロイやテストが容易なモノリスが最も迅速です。

💡 O'zbekcha: Kichik loyihada monolit tez va oson. Jamoa va tizim juda kattalashganda esa mikroxizmatlar foydali. Eng muhimi: loyiha bosqichiga qarab to'g'ri arxitektura tanlash.

📝 Intervyu Grammatikasi & Keigo Qoidalari (Oltin Qoliplar) 10 ta eng muhim qolip • HR psixologiyasi va to'g'ri/xato taqqoslari
〜てまいりました / 〜に従事してまいりました
Kenjōgo (Kamtarlik)
Ma'nosi: "... qilib kelganman / ... sohasida faoliyat yuritib keldim". O'tgan zamondagi barcha tajribalarni xushmuomala ifodalash qolipi.
💡 HR Psixologiyasi: Oddiy "〜ました" bolalarcha va quruq eshitiladi. "〜てまいりました" esa nomzodning jiddiy biznes etiketi va kamtarlik madaniyatiga egaligini darhol isbotlaydi.
❌ Oddiy (Xato):
「大学でWebアプリを開発しました。」
⭕️ Professional:
「大学で実践的なWeb開発に努めてまいりました。」
「これまで主にReactとNode.jsを用いたフルスタック開発に従事してまいりました。」
Shu paytgacha asosan React va Node.js yordamidagi full-stack ishlab chiqish bilan shug'ullanib kelganman.
〜させていただきたく存じます
Kenjōgo + Keigo
Ma'nosi: "Agar imkoniyat berilsa, ... qilishni chin dildan istardim". Eng yuqori darajadagi xushmuomalalik bilan o'z orzu va maqsadini bildirish.
💡 HR Psixologiyasi: "〜したいです" (qilishni xohlayman) shaxsiy talabdek yangraydi. "〜させていただきたく存じます" esa jamoaga qo'shilishga ruxsat so'rab minnatdorchilik bilan aytiladi.
❌ Oddiy (Xato):
「御社に入社したいです。」
⭕️ Professional:
「ぜひ貴社の一員として貢献させていただきたく存じます。」
「これまでの経験を活かし、貴社の多様な開発案件に挑戦させていただきたく存じます。」
Oldingi tajribamni ishga solib, kompaniyangizning turli xil dasturlash loyihalariga hissa qo'shishni chin dildan istardim.
〜と考えております / 〜と認識しております
Teineigo (Qat'iyat)
Ma'nosi: "Shunday deb qat'iy hisoblayman / shunday tushunchaga egaman". Noaniq "o'ylaymanki" emas, professional xulosa.
💡 HR Psixologiyasi: Yapon suhbatida "〜と思います" (menimcha) ko'p ishlatilsa nomzod o'ziga ishonchsizdek ko'rinadi. "〜と考えております" esa qat'iy mantiq va qarorni bildiradi.
❌ Noaniq (Xato):
「報連相はとても大切だと思います。」
⭕️ Professional:
「チーム開発において報連相は最重要であると考えております。」
「エンジニアの価値はコードを書くことだけでなく、顧客の課題を解決することにあると認識しております。」
Muhandisning qiymati faqat kod yozishda emas, balki mijoz muammolarini yechishda ekanligini chuqur tushunaman.
〜の経験を活かし、貴社に貢献できると考えております
Oltin Xulosa Qolipi
Ma'nosi: "... tajribamni to'liq ishga solib, kompaniyangiz rivojiga munosib hissa qo'sha olaman deb ishonaman".
💡 HR Psixologiyasi: O'z tajribangizni aytib bo'lgach, uni havoda qoldirmasdan CAL kompaniyasiga qanday foyda keltirishi bilan bog'lash 100% zarur.
❌ Havoda qolgan:
「私はReactが得意です。」
⭕️ Kompaniyaga bog'langan:
「Reactの実務経験を活かし、即戦力として貢献できると考えております。」
「大学や実践で培った自走力とWeb開発の経験を活かし、貴社に貢献できると考えております。」
O'quv va amaliyotda to'plagan mustaqil ishlash qobiliyatim hamda Web tajribamni ishga solib, kompaniyangizga hissa qo'sha olaman deb hisoblayman.
結論から申し上げますと、〜 (PREP usuli)
PREP Struktura
Ma'nosi: "Xulosadan boshlab gapiradigan bo'lsam, ...". Savolga darhol 1-jumlada to'g'ridan-to'g'ri aniq javob berish.
💡 HR Psixologiyasi: Yaponiyada eng ko'p baholanadigan narsa — mantiqiy va xulosani birinchi aytish (Point ➔ Reason ➔ Example ➔ Point). Uzun kirish so'zlar jiddiy minus beradi.
❌ Uzoqdan boshlash:
「私は大学に入って色々と勉強してきて...」
⭕️ PREP bilan boshlash:
「結論から申し上げますと、私の最大の強みは課題解決力です。」
「結論から申し上げますと、どのようなプロジェクト先でも適応できる柔軟性とコミュニケーション力です。」
Xulosadan boshlaydigan bo'lsam, bu qanday loyiha muhiti bo'lmasin tez moslasha oladigan egiluvchanligim va muloqotchanligimdir.

💡 HR Psixologiyasi: 面接官が言いました (Mentsukan aytdi) - juda qo'pol xato! "面接官がおっしゃいましたように" deyish shart.

Siz hozir to'g'ri ta'kidlaganingizdek, amaliyotda mustaqil tashabbus eng muhim talab ekanligini chuqur his qildim.
至らない点もございますが、〜
Kamtarlik & O'sish

💡 HR Psixologiyasi: Chet ellik nomzodlar ba'zida haddan ziyod o'zini maqtab yuborishadi. Bu ibora orqali siz kamchiliklarni tan oluvchi va o'rganishga ochiq (素直さ) ekaningizni ko'rsatasiz.
❌ O'ziga haddan ziyod bino qo'yish:
「私は完璧に何でもできます。」
⭕️ O'rganuvchan va samimiy:
「至らない点もございますが、素直に学び全力で努めます。」
「まだまだ至らない点も多々ございますが、先輩方のご指導を素直に吸収し、一日も早く貢献いたします。」
Hali kamchiliklarim ko'p bo'lsa-da, ustozlarning ko'rsatmalarini chin dildan o'rganib, tez orada jamoaga hissa qo'shaman.
恐れ入りますが、〜 / 大変失礼ながら、〜

Ma'nosi: "Kechirasiz, noqulay bo'lsa-da, ... / Izningiz bilan ...". Suhbatdoshga noqulaylik tug'dirmasdan iltimos qilish yoki qayta so'rash.
💡 HR Psixologiyasi: Savolni eshitmay qolganda "もう一度言ってください" deyish xunuk eshitiladi. "大変恐れ入りますが..." deb boshlash suhbatdoshni hurmat qilish belgisidir.
❌ Qo'pol buyruq:
「もう一度質問を言ってください。」
⭕️ Kushon bilan:
「大変恐れ入りますが、もう一度ご質問を伺ってもよろしいでしょうか。」
「大変恐れ入りますが、音声が途切れてしまいましたので、もう一度伺ってもよろしいでしょうか。」
Kechirasiz, ovoz bir oz uzilib qolgani sababli, savolingizni yana bir bor eshitsam maylimi?
〜を通じて、〜の重要性を学びました
Xulosa & Saboq
Ma'nosi: "... tajribasi orqali ... ning qanchalik muhim ekanligini chuqur anglab yetdim". Har bir texnik qiyinchilikdan to'g'ri xulosa chiqarish.
💡 HR Psixologiyasi: HR xatoga tushganingizni emas, xatodan qanday saboq olganingizni bilishni istaydi. Bu jumla hikoyani ajoyib xotima bilan yakunlaydi.
❌ Saboqsiz:
「バグを直して無事に終わりました。」
⭕️ Saboq va o'sish bilan:
「このトラブルを通じて、事前の負荷テストと報連相の重要性を学びました。」
「仕様変更への対応を通じて、密なコミュニケーションと設計書の重要性を深く学びました。」
Talablar o'zgarishini bartaraf etish orqali doimiy muloqot va loyiha hujjatlarining naqadar muhimligini chuqur o'rgandim.

5. Muammo Yechish (PREP)
Vaqt: ~75 soniya | Loyiha: Bionexstar
Texnik Muammoni Hal Qilish Tajribasi (Troubleshooting Nutqi)
📍 Qachon aytiladi: HR: "これまでの開発で一番苦労したことやトラブルは何ですか？どう解決しましたか？" deganda aytiladi.
「【結論】 開発において最も苦労したのは、『Bionexstar』プロジェクトにおける大量データ通信に伴うAPIのレスポンス遅延でした。 【理由・原因】 ユーザー体験を向上させるため原因を追究したところ、フロントエンドにおける不要な再レンダリングと、データベース側でインデックスが不足していたことによるスロークエリがボトルネックであると突き止めました。 【具体例・解決策】 そこで2つの対策を実行いたしました。 まずフロントエンドでは、ReactのuseMemoやuseCallbackを活用してコンポーネントの再描画を最小限に抑えました。 次にバックエンドでは、頻出する検索条件に対してデータベースの複合インデックスを追加し、さらにクエリの重複発行を削減いたしました。 【結果・学び】 その結果、APIの応答速度を約40％短縮し、スムーズなUI表示を実現いたしました。 この経験を通じて、思い込みで修正するのではなく、ログやプロファイラーを用いてボトルネックを論理的に特定し、チームに共有しながら改善する重要性を学びました。」
[Ketsuron] Kaihatsu ni oite mottomo kurō shita no wa, 'Bionexstar' purojekuto ni okeru tairyō dēta tsūshin ni tomonau API no responsu chien deshita. [Riyū/Gen'in] Yūzā taiken o kōjō saseru tame gen'in o tsuikyū shita tokoro, furontoendo ni okeru fuyō na sai-rendaringu to, dētabēsu gawa de indekkusu ga fusoku shite ita koto ni yoru surō-kueri ga botorunekku de aru to tsukitomemashita. [Gutairei/Kaiketsusaku] Soko de futatsu no taisaku o jikkō itashimashita. Mazu furontoendo dewa, React no useMemo ya useCallback o katsuyō shite konpōnento no sai-byōga o saishōgen ni osaemashita. Tsugi ni bakkuendo dewa, hinshutsu suru kensaku jōken ni taishite dētabēsu no fukugō indekkusu o tsuika shi, sarani kueri no chōfuku hakkō o sakugen itashimashita. [Kekka/Manabi] Sono kekka, API no ōtō sokudo o yaku 40-pāsento tanshuku shi, sumūzu na UI hyōji o jitsugen itashimashita. Kono keiken o tsūjite, omoikomi de shūsei suru no dewa naku, rogu ya purofairā o mochiite botorunekku o ronriteki ni tokutei shi, chīmu ni kyōyū shinagara kaizen suru jūyōsei o manabimashita.
"[Xulosa]: Dasturlashda eng ko'p qiyinchilik tug'dirgan holat — 'Bionexstar' loyihasida katta hajmdagi ma'lumotlar almashinuvi paytida API javob tezligining pasayishi bo'ldi. [Sabab]: Foydalanuvchi qulayligini saqlash uchun tahlil qilganimda, frontend'da ortiqcha qayta render bo'lishi hamda ma'lumotlar bazasida indekslar yo'qligi sababli sekin so'rovlar (slow queries) asosiy to'siq bo'layotganini aniqladim. [Amaliy yechim]: Ikkita aniq yechim qo'lladim: Birinchidan, frontend qismida React'ning useMemo va useCallback xuklaridan foydalanib komponentlarning keraksiz qayta chizilishini to'xtatdim. Ikkinchidan, backend qismida eng ko'p qidiriladigan ustunlar bo'yicha bazaga qo'shma indekslar qo'shib, takroriy SQL so'rovlarni qisqartirdim. [Natija va Saboq]: Natijada API tezligini qariyb 40% ga qisqartirishga va qotmaydigan yengil interfeysga erishdim. Ushbu tajriba menga taxmin bilan emas, balki loglar va tahlil vositalari orqali muammo o'zagini aniq topish hamda jamoa bilan maslahatlashib tuzatish zarurligini o'rgatdi."
